# Option D design: in-process dosemu2 plugin for Hydra hosting

**Scope:** research/design doc for Track 4 Option D — a `src/plugin/hydra/` in the local dosemu2 fork that hosts the Hydra runtime in-process. Docs only; no plugin code in this phase.
**Validation authority:** SST (SingleStepTests hardware captures) is the validation authority; dosemu2's role is Hydra hosting, not validation.
**Pinned dosemu2:** `604ce0cdd1a71f657e2a2df623d216d5ab289313` (the same base the frozen carrier is pinned to).
**Status:** forward-looking design research; not a superseded document.

Hydra's bridge contract is `hydra_machine.h` (`/home/p/dis86/hydra/src/hydra_machine.h`): a `hydra_machine_hardware_t` vtable (`mem_hostaddr`, `mem_read8/16`, `mem_write8/16`, `io_in8/16`, `io_out8/16`, `state_save`, `state_restore`, `update_registers`) plus the lifecycle functions `hydra_machine_init`/`exec`/`notify`/`step_hook`. dosemu2 is the hosting emulator. This document is the design for how the hosting plugin attaches: the gate analysis of whether a PC-boundary hook can be had with zero core edits (it cannot), the plugin-architecture survey, the mapping of the Hydra vtable onto dosemu2 internals, the local-fork logistics, the open questions, and a phased implementation sketch.

## 1. The crux gate: can a PC-boundary hook be had with zero core edits?

**Question (from `plan.md:21`):** can `src/plugin/hydra/` obtain a PC-boundary hook with zero core edits, including driving the frozen simx86 boundary hook in-process?

**Decision: NO. A minimal core callback registration is unavoidable.** A `src/plugin/hydra/` cannot obtain a PC-boundary hook without a small, guarded change to simx86 core. The evidence:

1. **The debugger — the closest analog — registers nothing.** The debugger's hook is TF/EXCP01_SSTP single-step plus int3/interrupt-vector intercepts plus poll points, NOT a registered per-instruction callback. It gets control only because core is compiled with `USE_MHPDBG` and contains hardcoded `mhp_debug(DBG_TRAP…)` call sites. There is no `register_step_callback` API (repo-wide search returns nothing). Core calls the debugger through hardcoded `#ifdef USE_MHPDBG` call sites; `USE_MHPDBG` is a compile-time global from `src/plugin/debugger/config/plugin_config.h:1` merged into `plugin_config.hh` via `mkpluginhooks`, activating ~30 `#ifdef USE_MHPDBG` blocks at key boundary call sites: `do_vm86.c:564` (vm86 single-step/breakpoint), `dpmi.c:5688-5690` (DPMI single-step/breakpoint), `do_vm86.c:556` (vm86 interrupt), `do_vm86.c:60` (vm86_fault), `dpmi.c:2879,3995,4110,4186,4203` (DPMI interrupt intercepts), `signal.c:846` (poll). The debugger chain is: `mhp_trace()` (`mhpdbgc.c:813-888`) → `set_TF()` → in simx86 `FindExecCode()` (`interp.c:431-517`) at `:446-448` the TF bit is converted to `MSSTP` + `MTRAP` (`codegen.h:186-187`); `JMPGen()` emits `EXCP01_SSTP` at every node tail (`interp.c:153-154`); `Interp86()` returns on `TheCPU.err` (`interp.c:514`); `e_vm86_tail()` maps `EXCP01_SSTP` → `VM86_TRAP + (1<<8)` (`cpu-emu.c:1049-1051`); `_do_vm86()` calls `mhp_debug(DBG_TRAP + (1<<8), 0, 0)` (`do_vm86.c:561-564`), which sets `stopped=1` and returns `rtncd=1` to suppress the architectural INT 1 (`mhpdbg.c:526-546`). The boundary is published OUTSIDE simx86 in the VM86_TRAP/DPMI trap dispatch layers; ZERO `mhp_*` calls live inside simx86 core files (`interp.c`/`cpu-emu.c` only `#include "mhpdbg.h"`).
2. **A plugin cannot subscribe to those compile-time-wired call sites.** No generic observer list exists in simx86. `FindExecCode()` (`interp.c:431-517`) loop is: set MSSTP|MTRAP from TF (`:446-448`) → `_Interp86`/`FindTree` (`:449-472`) → `PC = DoExec(G)` (`:503`) → return if `TheCPU.err` (`:514`). No hook list, observer array, or callback field. `HandleEmuSignals()` (`codegen.c:635-660`) handles async exit flags, not pluggable observers.
3. **The per-instruction granularity both the debugger and the frozen patch get comes from MSSTP/MTRAP/EXCP01_SSTP.** `EXCP01_SSTP = 2` (`src/base/emu-i386/simx86/emu86.h:661`); `TheCPU.err` stores `exception_number + 1`. Intercepting at that point requires adding something to `FindExecCode()` — exactly what the frozen patch does at `patch:733` (validator before each node at top of the loop) and `patch:758-759` (validator after each node).
4. **The frozen patch's approach is structurally the only option for an in-emulator PC-boundary hook.** The frozen patch 0001 (`/home/p/dis86/patches/dosemu2/0001-simx86-add-executable-scoped-validator-control.patch`) is 2 new files in `simx86/` plus a 17-line change to `interp.c`: `diis_state = diis_validator_before_node(&PC);` at the top of the `FindExecCode` loop (`patch:733`); when active it forces single-instruction nodes with `TheCPU.mode |= MSSTP;` (`patch:740`) — the same MSSTP bit the debugger gets via TF; after each node `diis_validator_after_node(diis_start_pc, PC, diis_decoded_instructions, TheCPU.err);` (`patch:758-759`), with `diis_start_pc = G->key` (`patch:748`) and `diis_decoded_instructions = G->seqnum` (`patch:749`); fault classification excludes the deliberate single-step: `if (cpu_err >= EXCP00_DIVZ && cpu_err <= EXCP12_MCHK && cpu_err != EXCP01_SSTP) flags |= DIIS_STEP_FAULT;` (`patch:651-653`).

**Recommended cleaner design:** rather than hardcoding `diis_validator_before_node`/`after_node` as the frozen patch does, convert those two calls into a function-pointer slot (registration indirection) that a plugin sets through a core-exported setter (e.g. `simx86_register_boundary_hook(fn)`). This is a slightly larger but still minimal core change — the slot lives in `FindExecCode()` at the exact positions `patch:733` and `patch:758-759` occupy — and it lets `hydra/` live entirely in `src/plugin/` with no per-plugin `#ifdef` wiring. Section 4 details this.

**Freeze-gate implication:** any core edit the plugin requires must clear the freeze's mandatory change gate (`FREEZE_ABI_V1.md:74-83`), including item 4: "a documented attempt to solve the defect through the generic hook/module interface before changing dosemu2 core code" (`FREEZE_ABI_V1.md:81`). A function-pointer registration slot IS the "generic hook/module interface" path the gate prefers; a `src/plugin/hydra/` implementation is that interface made concrete.

## 2. dosemu2 plugin architecture (survey findings)

### Directory layout and required files

Each plugin lives in `src/plugin/<name>/`. Required files: `Makefile`, `configure.ac`, optional `Makefile.conf.in`, optional `config/plugin_config.h` (feature macro such as `USE_HYDRA`), and sources. No template directory exists; `debugger`/`dnative`/`slirp` are the de-facto templates.

### Discovery and registration

Registration is an explicit registry list, not directory auto-discovery. `plugin_list` at the repo root lists enabled plugins (`plugin_list:23` lists `debugger`). Top-level `configure.ac:543` reads it. `--enable-plugins=list` / `--disable-plugins` / `+` append selects (`configure.ac:544-552`). For each enabled plugin, `configure.ac:615-628` loops: calls `scripts/plugctl.sh $i yes` (`:617`), adds to `PLUGINSUBDIRS` (`:618`), and — if no `NO_LIB` marker and (no `USE_DL_PLUGINS` or dlplugins disabled) — adds to `ST_PLUGINSUBDIRS` (static set, `:619-622`); if `Makefile.conf.in` exists, adds `plugin/$i/Makefile.conf` to `CONFFILES` (`:623-625`). `scripts/plugctl.sh:16-38` performs per-plugin configure (symlinks `configure.ac`/`Makefile.conf.in`, runs autoreconf, runs `./configure`, writes `config/plugin_enable`). `scripts/mkpluginhooks` generates `src/plugin/plugin_config.hh` by including each enabled plugin's `config/plugin_config.h` (`mkpluginhooks:47-57`), pulled in by `src/include/plugin_config.h:1` → every TU via `dosemu_config.h`.

**Adding a new plugin = create `src/plugin/<name>/` with the required files AND append the name to `plugin_list`.**

### Link model

Both static and dynamic exist.

- **Static (base):** each plugin compiles to a static archive (`src/Makefile.common.post:19-23,60-63`); `src/arch/linux/Makefile.main:57-61` puts plugins in `ST_LIBSUBDIRS`; default `SOLIB=1` links all `lib/lib*.a` with `--whole-archive` into `libdosemu2.so.0.1` (`Makefile.main:89-101`); `dosemu2.bin` links `-ldosemu2` (`Makefile.main:109-111`).
- **Dynamic (opt-in per plugin via `USE_DL_PLUGINS=1`):** builds `bin/libplugin_<name>.so` with `PLUGIN_LDFLAGS=-shared` (`configure.ac:793-797`); core dlopens via `load_plugin("name")` → `dlopen` (`src/base/misc/utilities.c:815-850`); the main binary is built `-rdynamic` (`configure.ac:424`) so core symbols are visible.
- The debugger is purely static (no `.so` target, `src/plugin/debugger/Makefile:12`).

### Init entry point

Standardized init ABI in `src/include/init.h`: `CONSTRUCTOR(X)` (GCC constructor, `init.h:4`); `CONSTRUCTOR2(x)` (DL: constructor; static: defines `plugin_x()`, `init.h:8`); `LOAD_PLUGIN(x)` (DL: `load_plugin("x")`; static: declare-and-call `plugin_x()`, `init.h:11,14`). Three observed patterns:

1. **Core-initiated via `LOAD_PLUGIN`:** e.g. `LOAD_PLUGIN(json)` at `src/base/init/config.c:1177`; `LOAD_PLUGIN(msdos)` at `src/dosext/dpmi/msdoshlp.c:732`.
2. **Self-registering constructor:** e.g. `CONSTRUCTOR(static void init(void)) { register_dnative_ops(&ops); }` at `src/plugin/dnative/dnative.c:1041-1043`; video `register_video_client` at `src/plugin/sdl/sdl.c:1837-1843` and `term/terminal.c:900-902`; audio `pcm_register_player` at `src/plugin/sdl/snd_o_SDL.c:143-145`.
3. **Debugger-style:** no constructor; core hardcodes direct calls guarded by `USE_MHPDBG` (`mhp_early_init()` at `src/base/core/emu.c:322-324`; `mhp_init()` at `emu.c:389-391`; `mhp_debug(...)` at ~20 sites).

### Public vs internal boundary

There is NO `plugin.h` with `register_callback`/`signal_emit`/`mem_get_addr`. Plugins include internal core headers (`emu.h`, `utilities.h`, `init.h`, `timers.h`, `sig.h`, `ioselect.h`, `video.h`, `cpu.h`, `bios.h`, `memory.h`, `vgaemu.h`, `dosemu_config.h`) and call internal functions directly. Key registration functions (the de-facto API): `register_video_client(struct video_system*)` (`src/include/video.h:148`); `pcm_register_player/recorder/efp` (`src/base/sound/sndpcm.c:1154,1170,1184`); `hlt_register_handler_vm86(emu_hlt_t)` (`src/include/emu.h:516`, used by debugger `mhpdbgc.c:803`); `add_to_io_select` (`src/include/ioselect.h:6-13`); `mfs_define_drive` (`src/include/redirect.h:57`); `register_dnative_ops` (`src/dosext/dpmi/dnative/dnative.h:28`); `load_plugin`/`close_plugin` (`src/base/misc/utilities.c:815-864`).

The debugger is the most internal case — its header `mhpdbg.h` lives in the core include dir, and core calls it from ~20 files under `#ifdef USE_MHPDBG`. Even clean DL plugins (`sdl.c`, `slirp.c`, `msdos.c`, `fdpp.c`, `dnative.c`) `#include` internal headers and call internal functions. The only real contracts: (1) `init.h` macros, (2) the feature macro via `config/plugin_config.h`, (3) whatever registration functions core declares in headers.

**Implication for hydra:** if Hydra hosting only needs to register a provider and act on events the core already dispatches (the `dnative`/`register_video_client` pattern), it can be a self-contained plugin (constructor + `register_*` + one line in `plugin_list`) — no core edits. If it needs to hook core execution where no registration interface exists (the debugger's trap/int hooks), it requires adding guarded call sites in core (the `USE_MHPDBG` pattern) or a new registration interface. There is no generic callback/event API. Hydra's PC-boundary hook is exactly the second case — hence the crux decision in Section 1.

## 3. Boundary hook design (the minimal core callback)

The design converts the frozen patch's hardcoded `diis_validator_*` calls into a registration slot.

- **Insertion points:** top of the `FindExecCode()` loop before node selection (`interp.c:431-517`), at the position of `patch:733`; and after `PC = DoExec(G)` (`interp.c:503`), at the position of `patch:758-759`.
- **Slot shape:** a function-pointer slot in simx86, initially NULL, with a core-exported setter (e.g. `simx86_register_boundary_hook(before_fn, after_fn)` declared in a simx86 header reachable by plugins). The `before` callback receives the PC and may force single-instruction nodes by setting the same `MSSTP` bit (`TheCPU.mode |= MSSTP;`, as at `patch:740`); the `after` callback receives start PC, returned PC, decoded instruction count (`G->seqnum`, per `patch:749`), and `TheCPU.err`. Fault classification excludes the deliberate single-step exactly as the frozen patch does: `if (cpu_err >= EXCP00_DIVZ && cpu_err <= EXCP12_MCHK && cpu_err != EXCP01_SSTP) flags |= DIIS_STEP_FAULT;` (`patch:651-653`).
- **Registration:** the plugin registers via a constructor at load (self-registering constructor pattern, `init.h:4`) or via `LOAD_PLUGIN` from core (`init.h:11,14`). No `#ifdef USE_HYDRA` wiring anywhere; the slot is neutral and the plugin owns policy.
- **Difference from the frozen patch:** the frozen patch 0001 hardcodes `diis_validator_before_node`/`after_node` and carries the whole validator state machine inside simx86. The slot keeps simx86 free of plugin policy — one NULL-checked indirection — and moves all Hydra logic into `src/plugin/hydra/`.
- **MSSTP forcing:** both the debugger (via TF, `interp.c:446-448`) and the frozen patch (via `patch:740`) force single-instruction nodes so the boundary is instruction-granular. The slot design must do the same when the hook is active; with MSSTP set, one node = one instruction, so a node boundary is an instruction boundary.
- **Freeze-gate implication:** this is precisely the "generic hook/module interface" item 4 of the mandatory change gate (`FREEZE_ABI_V1.md:81`) prefers. The frozen carrier is not modified; the slot is a new, separate change subject to the gate's other items (checked-in fixture, defect classification, ABI compatibility analysis).

## 5. Local-fork logistics

- **Fork stays local; created at the pinned base.** `FREEZE_ABI_V1.md` has NO explicit fork recommendation — it pins upstream (`FREEZE_ABI_V1.md:7` — `604ce0cdd1a71f657e2a2df623d216d5ab289313`), names the 2-patch carrier (`:8`), and establishes the mandatory change gate (`:74-83`). The actual fork recommendation is in `patches/dosemu2/README.md:223-229` ("Upstreaming later"): "Once a writable dosemu2 fork exists, replay these two frozen feature commits with `git am` onto the pinned base, push those commits to the fork, and make the fork PR the authoritative implementation. At that point this local carrier can either be regenerated from the fork commits or removed once the integration fetches the fork directly." So **patches move INTO the fork as git history; the dis86-side carrier becomes optional afterward.** (Note: `plan.md:23` attributes this to FREEZE_ABI; the recommendation text actually lives in the carrier README.)
- **Pinned base must be fetched.** The shallow clone HEAD is `82770ab` — DIFFERENT from the pinned base — and the shallow clone does NOT contain the pinned base object (`git cat-file -t 604ce0cd…` → bad object). Fork creation must fetch `604ce0cd…` first (unshallow or fetch that specific SHA). Delta = upstream devel history since 2026-08-06; large and irrelevant to the carrier. Rebasing onto newer upstream should be explicit and reviewed (`patches/dosemu2/README.md:21-22`).
- **`scripts/apply-dosemu2-patches.sh` automates only `git am`.** It hard-codes `expected_base=604ce0cd…` (`:4`); refuses non-git (`:12-15`), wrong HEAD (`:17-23`), dirty worktree (`:25-28`); validates `series` has exactly the 2 frozen patches (`:30-41`); runs `git am` (`:43-48`).
